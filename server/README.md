# Сервис заявок

Принимает заявки с формы записи, хранит их у себя и заводит карточки
в Битрикс24.

## Зачем он вообще нужен

Форма могла бы бить в вебхук Битрикса напрямую из браузера. Тогда адрес
вебхука лежал бы в открытом виде в исходниках страницы — а он равносилен
паролю от CRM: кто его знает, тот читает и пишет карточки. Так делать нельзя.

Второе: по 152-ФЗ (ст. 18 ч. 5) данные граждан РФ должны попадать в базу
**на территории России**. Поэтому первичное хранилище — SQLite на российском
сервере, и уже оттуда данные расходятся дальше.

Третье: CRM может не ответить — лежит портал, моргнула сеть, упёрлись
в лимит запросов. Пациенту в этот момент уже сказано «спасибо», и потерять
его нельзя. Поэтому порядок такой: сначала запись в свою базу, ответ
человеку — и только потом отправка. Не приняли — дошлём фоновым повтором.

```
Форма на сайте
      │  POST /api/lead
      ▼
   leads.py ──► SQLite (/var/lib/kleomed/leads.db)   ← первичное хранилище
      │
      ├──► Битрикс24: crm.lead.add                   — сразу, повтор при сбое
      │
      └──► MAX: «заявка №142, имя, телефон»          — сигнал владельцу
```

## Что уходит в Битрикс24

Через **входящий вебхук** портала, методом `crm.lead.add`:

| Поле карточки | Что в нём |
|---|---|
| `TITLE` | `Заявка с сайта № 142 — Имплантация` |
| `NAME` | как человек представился в форме |
| `PHONE` | `+79119377727`, тип «мобильный» |
| `SOURCE_ID` | `WEB` — «Сайт» |
| `SOURCE_DESCRIPTION` | какая именно форма: модалка или блок на странице |
| `COMMENTS` | услуга, пожелание по времени, страница, откуда пришёл |
| `UTM_*` | метки рекламы, если человек пришёл по объявлению |

Точное время визита намеренно не ставим. Форма спрашивает не час, а часть
дня — «утро», «день», «вечер». Записать из этого конкретное время значит
занять слот тем, о чём пациент не договаривался. Пожелание уходит
в комментарий, а час назначает администратор.

### Лиды или сделки

Новые порталы Битрикс создаёт в «простом режиме», где лидов не существует
вовсе, и `crm.lead.add` там возвращает ошибку. Проверьте левое меню CRM:

* есть раздел **«Лиды»** → `KLEOMED_B24_ENTITY=lead` (по умолчанию);
* раздела нет → `KLEOMED_B24_ENTITY=deal` — сервис заведёт контакт
  с телефоном и сделку на него.

### Если Битрикс не принял

Заявка остаётся в базе с пустым `crm_id`, в журнале появляется строка
с текстом ошибки *от самого Битрикса* (он объясняет причину внятнее, чем
код ответа). Раз в 5 минут сервис пробует дослать — до 24 попыток и не
старше недели. Дальше это разговор с администратором, а не вечный стук
в чужой API.

На странице `/admin` у каждой заявки видно, дошла ли она: номер карточки,
`ждёт` или `не ушла`. Заявка, потерянная молча, — худшее, что может быть,
поэтому состояние доставки видно там же, где телефон.

## Почему в MAX уходят имя и телефон

Раньше в мессенджер шёл обезличенный сигнал «пришла заявка №142» — из-за
Telegram: его серверы за рубежом, а в карточке ООО «Клеомед» в реестре
Роскомнадзора в графе трансграничной передачи стоит «Нет». У MAX серверы
в России, и этот довод отпал.

Что остаётся помнить: сам факт обращения к стоматологу составляет врачебную
тайну (323-ФЗ ст. 13). Значит, чат с ботом должен быть **личным чатом
владельца**, а не общей группой, и телефон с этим чатом — под замком.
Вернуть обезличенный сигнал можно настройкой `KLEOMED_MAX_DETAILS=0`.

## Точки входа

| Метод и адрес | Кто ходит | Защита |
|---|---|---|
| `POST /api/lead` | форма на сайте | антифлуд по IP |
| `GET /admin?token=…` | администратор клиники | токен в адресе |
| `GET /health` | мониторинг | нет |
| `GET /GetTickets` | IDENT, если вернёмся к нему | заголовок `IDENT-Integration-Key` |
| `GET /GetOngoingCalls`, `/GetFinishedCalls` | то же | тот же ключ, отвечают пустым списком |

Клиника выбрала Битрикс24, но точки опроса под IDENT оставлены на месте:
он забирает заявки сам, раз в две минуты, и если когда-нибудь понадобится —
достаточно вписать ключ. Пока `KLEOMED_IDENT_KEY` пуст, они отвечают `503`,
и это осознанно: лучше явная ошибка, чем молча открытая наружу выдача заявок.

## Установка

```bash
# пользователь без домашнего каталога и без входа в систему
useradd --system --no-create-home --shell /usr/sbin/nologin kleomed

install -d -m 755 /opt/kleomed
install -m 644 leads.py /opt/kleomed/leads.py

install -d -m 750 /etc/kleomed
install -m 600 leads.env.example /etc/kleomed/leads.env
$EDITOR /etc/kleomed/leads.env          # вписать вебхук и ключи

install -m 644 kleomed-leads.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now kleomed-leads
systemctl status kleomed-leads
```

Сайт кладём в `/var/www/kleomed/site`, nginx настраиваем по
`nginx.conf.sample`, сертификат берём через `certbot --nginx`.

Зависимостей нет — только Python 3.9+ из системы. Ни pip, ни venv.

## Ключи

Вебхук Битрикса берётся в портале (см. `leads.env.example`). Остальное
генерируется здесь:

```bash
openssl rand -hex 24    # для KLEOMED_ADMIN_TOKEN
openssl rand -hex 32    # для KLEOMED_IDENT_KEY, если он вдруг понадобится
```

## Проверка после установки

```bash
curl https://клеомед.рф/health

curl -X POST https://клеомед.рф/api/lead \
  -H 'Content-Type: application/json' \
  -d '{"name":"Проверка","phone":"+79119377727","consent":true}'
```

В журнале должно появиться `заявка №N заведена в Битрикс24`, а в портале —
карточка. Тестовую заявку потом удалить в обоих местах:

```bash
sqlite3 /var/lib/kleomed/leads.db "DELETE FROM leads WHERE name='Проверка';"
```

## Резервная копия

В базе персональные данные — копию храним на том же российском сервере
или на российском же хранилище, не в зарубежном облаке.

```bash
sqlite3 /var/lib/kleomed/leads.db ".backup '/var/backups/kleomed-$(date +%F).db'"
```

## Сроки хранения

152-ФЗ требует удалять данные, когда цель обработки достигнута. Заявка своё
отработала, как только пациент записан и попал в CRM. Разумно чистить базу
раз в квартал — точный срок должен назвать ответственный за обработку ПДн:

```bash
sqlite3 /var/lib/kleomed/leads.db \
  "DELETE FROM leads WHERE created_ts < strftime('%s','now','-180 days');"
```
